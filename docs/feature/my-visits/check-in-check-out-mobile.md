# Check-in & Check-out — Mobile Integration Guide

**For:** Flutter (mobile app) developers
**Backend status:** implemented 2026-10-05 (migration `AddVisitCheckOutOutcomes`).
**Requirements and design:** [check-in-check-out-api.md](check-in-check-out-api.md) (see its §0 for decisions).
This guide covers only what the app has to do.

---

## 1. What changes for the app

| Today | After this integration |
|---|---|
| Check-in and check-out go to the server only inside `POST /visits/push`. | **Online:** call `POST /check-ins` and `POST /check-outs` directly and show the server's answer. **Offline:** keep queueing through `/push` as now. |
| The stop's state on screen is the phone's own copy. | Every stop in the route pull carries a **`visit`** object: the server's state. Adopt it once your local rows are sent. |
| Check-out has no outcome. | The rep picks **Check out with order** or **Check out without order** (reason from a server list). |
| A quotation isn't tied to the visit. | Send **`clientId`** and **`stopId`** when creating a quotation during a visit. |

The server treats a record **identically** whether it arrives online or through `/push`. Use **the same ids** on both paths.

---

## 2. Endpoints

Base: `/api/v1/mobile`. All need the bearer token.

| # | Method & path | Permission | Use |
|---|---|---|---|
| A | `POST /visits/check-ins` | `visits.create` | Check in (online) |
| B | `POST /visits/check-outs` | `visits.create` | Check out (online) |
| C | `GET /visits/stops/{stopId}/visit` | `visits.read` | Confirm one stop's state |
| D | `GET /visits/check-out-reasons` | `visits.read` | "No order" reasons, cached for offline use |
| E | `POST /visits/push` | `visits.create` | Offline batch, with new optional fields |
| F | `GET /visits/routes`, `/routes/delta` | `visits.read` | Each stop now has `visit` |
| G | `POST /quotations` | `quotations.create` | New optional `clientId`, `stopId` |

### Response envelopes

Success (all endpoints):

```json
{ "success": true, "message": "Checked in successfully.", "data": { ... }, "traceId": "…", "timestamp": "…" }
```

Error (RFC 9457 problem document). **Branch on `status` + `errorCode`**, never on the English `detail`:

```json
{
  "type": "https://docs.isigroup.com.kh/errors/Visit.AlreadyCheckedIn",
  "title": "The request conflicts with the current state of the resource.",
  "status": 409,
  "detail": "This stop already has an open check-in. …",
  "errorCode": "Visit.AlreadyCheckedIn",
  "correlationId": "…",
  "details": { /* VisitDto — only on the three 409s below */ },
  "errors": { /* field → messages — only on 400 General.Validation */ }
}
```

## 3. Ids: the rule everything depends on

| Id | Generated by | Notes |
|---|---|---|
| `stopId`, `routeId` | Server (**GUID strings**) | From the route pull. |
| Check-in `id` | **App** (UUID recommended, ≤ 64 chars) | Also the **visit id**. Keep it: check-outs reference it as `checkInId`. |
| Check-out `id` | **App** | |
| Quotation `clientId` | **App** | Generate it **when the rep starts the order**, before any network call. |
| Photo `id` | **App** | List them in the check-in's `photoIds`. A photo may upload later. |

Every write is idempotent on its id. Re-sending after a timeout is always safe and never creates a duplicate.

## 4. Check-in — `POST /visits/check-ins`

```json
{
  "id": "6f1c2a8e-…",
  "stopId": "0199c1a2-…",
  "routeId": "0199c19f-…",
  "timestamp": "2026-10-05T09:12:44+07:00",
  "latitude": 11.5621,
  "longitude": 104.9160,
  "accuracy": 8.5,
  "distanceFromDepot": 23.0,
  "isMocked": false,
  "overrideReason": "Shop moved across the street",
  "photoIds": ["ph-a1", "ph-a2"]
}
```

| Field | Req. | Notes |
|---|---|---|
| `id`, `stopId`, `timestamp`, `latitude`, `longitude`, `accuracy` | ✔ | `timestamp` = device clock **with offset**. Latitude −90..90, longitude −180..180, accuracy ≥ 0. |
| `routeId` | – | If sent, the stop must be on that route (else 404). |
| `distanceFromDepot` | – | Metres from the shop pin. `distanceFromCustomer` is also accepted. Evidence only; the server measures its own. |
| `isMocked` | – | Send the truth. It is **stored and flagged, never refused**. |
| `overrideReason` | – | Only when checking in outside the geofence. Omit the field otherwise. |
| `photoIds` | – | ≤ 20 ids. |

**No GPS fix?** Send `0, 0`. It is stored as `unverifiable`, not refused.

**200** → `data` is a `VisitDto` (§8) with `status: "checkedIn"`.

| Error | Meaning | What the app does |
|---|---|---|
| 409 `Visit.AlreadyCheckedIn` | Stop already has an open check-in with **another** id | **Adopt** `details` (the server's visit): replace the local check-in id with `details.visitId`. Don't retry. |
| 409 `Visit.AlreadyCompleted` | Stop already visited today | Show "Already visited". Offer an **ad hoc visit** for a return trip. Adopt `details`. |
| 404 `Visit.StopNotFound` | Stop not on your routes (or not on `routeId`) | Refresh routes. Drop the local row. |
| 422 `Visit.StopMismatch` | This `id` was already used on a different stop | Bug: generate ids per check-in. |
| 400 `General.Validation` | Bad field | Show `errors`. |

Same `id` again → **200**, same visit. Safe after a timeout.

> If the rep still has another stop open (the app should prevent this), the server closes that stop as **inferred** (`departureInferred: true`, outcome `unknown`) and accepts the new check-in.

## 5. Check-out — `POST /visits/check-outs`

Two shapes, chosen by `outcome`.

**(A) With order**

```json
{
  "id": "91be07…",
  "checkInId": "6f1c2a8e-…",
  "stopId": "0199c1a2-…",
  "timestamp": "2026-10-05T09:58:10+07:00",
  "latitude": 11.5622,
  "longitude": 104.9161,
  "durationMinutes": 45,
  "visitSummary": "Ordered rebar for next week",
  "outcome": "withOrder",
  "orders": [
    { "clientId": "qt-local-5521", "quotationId": "0199c3…" },
    { "clientId": "qt-local-5522", "quotationId": null }
  ]
}
```

**(B) Without order**

```json
{
  "id": "91be07…",
  "checkInId": "6f1c2a8e-…",
  "stopId": "0199c1a2-…",
  "timestamp": "2026-10-05T09:58:10+07:00",
  "latitude": 11.5622,
  "longitude": 104.9161,
  "durationMinutes": 20,
  "outcome": "withoutOrder",
  "noOrderReason": "boughtFromCompetitor",
  "noOrderNote": "Bought from ABC Steel"
}
```

| Field | Req. | Notes |
|---|---|---|
| `id`, `stopId`, `timestamp`, `latitude`, `longitude` | ✔ | |
| `checkInId` | ✔ (send it) | The check-in `id` this closes. |
| `durationMinutes` | ✔ | ≥ 0, device-measured. |
| `visitSummary` | – | ≤ 2,000 chars. |
| `outcome` | ✔ | `withOrder` \| `withoutOrder`. |
| `orders[]` | withOrder: ≥ 1 | `clientId` always. `quotationId` if you already have the server's id, else `null`. `type` optional (`quotation` default). Max 50. |
| `noOrderReason` | withoutOrder | A `code` from §6. |
| `noOrderNote` | if the reason has `requiresNote` | ≤ 500 chars. Always required for `other`. |

**200** → `VisitDto` with `status: "checkedOut"` and a `checkOut` block. Orders not yet on the server show `linkStatus: "pending"`. That is normal: they link when the quotation arrives.

| Error | Meaning |
|---|---|
| 422 `Visit.OutcomeRequired` | No `outcome` |
| 422 `Visit.OrderRequired` | `withOrder` with no orders |
| 422 `Visit.NoOrderReasonRequired` | No reason, or the reason needs a note and none was sent |
| 422 `Visit.UnknownNoOrderReason` | Code not in the list. Refresh the reason cache. |
| 422 `Visit.StopMismatch` | `checkInId` belongs to another stop |
| 409 `Visit.AlreadyCheckedOut` | Visit already closed by a **different** check-out id. Adopt `details`. |
| 404 `Visit.StopNotFound` | Not your stop |

Same check-out `id` again → **200**.

A check-out whose check-in hasn't reached the server yet is **accepted**. Its `checkOut.issues` contains `checkOutBeforeCheckIn` until the check-in arrives.

> The online endpoint is **strict** (422) because the rep can fix it on screen. The same row through `/push` is **accepted and flagged** instead. Validate on the client so the two paths behave the same for the rep.

## 6. No-order reasons — `GET /visits/check-out-reasons`

```json
{ "success": true, "data": [
  { "code": "stockStillEnough",     "nameEn": "Shop still has enough stock", "nameKm": "ហាងនៅមានស្តុកគ្រប់គ្រាន់", "requiresNote": false, "sort": 1 },
  { "code": "ownerNotAvailable",    "nameEn": "Owner / buyer not available", "nameKm": "…", "requiresNote": false, "sort": 2 },
  { "code": "priceTooHigh",         "nameEn": "Price too high",              "nameKm": "…", "requiresNote": false, "sort": 3 },
  { "code": "orderedByPhone",       "nameEn": "Will order by phone later",   "nameKm": "…", "requiresNote": false, "sort": 4 },
  { "code": "boughtFromCompetitor", "nameEn": "Bought from a competitor",    "nameKm": "…", "requiresNote": true,  "sort": 5 },
  { "code": "other",                "nameEn": "Other",                       "nameKm": "…", "requiresNote": true,  "sort": 99 }
] }
```

- **Cache it** (refresh on app start / route pull) so check-out works offline.
- Show `nameKm` / `nameEn` by app language. **Send `code`**. Codes never change; names can.
- Sort by `sort`. When `requiresNote` is true, make the note field required.
- Don't hard-code the list. It is provisional (sales ops may change it).

## 7. Creating a quotation during a visit — `POST /quotations`

Add two fields to the existing body:

```json
{ "customerId": "…", "shipmentType": "Pickup", "shipTo": null,
  "clientId": "qt-local-5521", "stopId": "0199c1a2-…" }
```

| Field | Notes |
|---|---|
| `clientId` | **New.** Same id you put in the check-out's `orders[].clientId`. The idempotency key: sending it again returns the existing quotation with **200** (a new one gives **201**). Treat both as success. |
| `stopId` | **New**, optional. The stop where the order was taken. Must be one of your stops (else 404 `Visit.StopNotFound`). Omit for an off-visit order. |

Store the returned `data.id` locally as the quotation's server id. Send it as `orders[].quotationId` in later check-outs if you have it; the server also matches on `clientId`, so it isn't required.

## 8. `VisitDto`: the server's view (responses of A, B, C, and `stops[].visit` in F)

```json
{
  "visitId": "6f1c2a8e-…",
  "stopId": "0199c1a2-…",
  "status": "checkedOut",
  "checkIn": {
    "id": "6f1c2a8e-…",
    "timestamp": "2026-10-05T02:12:44Z",
    "receivedAt": "2026-10-05T02:12:46Z",
    "geofence": "inside",
    "flagged": false,
    "overrideReason": null,
    "photoIds": ["ph-a1", "ph-a2"]
  },
  "checkOut": {
    "id": "91be07…",
    "timestamp": "2026-10-05T02:58:10Z",
    "receivedAt": "2026-10-05T02:58:12Z",
    "durationMinutes": 45,
    "outcome": "withOrder",
    "orders": [
      { "clientId": "qt-local-5521", "quotationId": "0199c3…", "linkStatus": "linked",  "type": "quotation" },
      { "clientId": "qt-local-5522", "quotationId": null,      "linkStatus": "pending", "type": "quotation" }
    ],
    "noOrderReason": null,
    "noOrderNote": null,
    "departureInferred": false,
    "issues": []
  },
  "updatedAt": "2026-10-05T02:58:12Z"
}
```

| Field | Values / meaning |
|---|---|
| `status` | `pending` · `checkedIn` · `checkedOut` · `missed` |
| `checkIn.geofence` | `inside` · `outside` · `unverifiable` (no pin or no GPS) |
| `checkIn.flagged` | Needs supervisor review (mock location, outside geofence, impossible travel…). Optionally show a small badge. |
| `checkOut.id` | `null` when the server closed the visit itself (`departureInferred: true`): the end-of-day sweep, or the rep checked in elsewhere. |
| `checkOut.outcome` | `withOrder` · `withoutOrder` · `unknown` (older app or inferred) |
| `orders[].linkStatus` | `linked` · `pending` (quotation not arrived yet) · `orderMissing` (pending > 72 h) |
| `checkOut.issues` | `incompleteOutcome` · `unknownReason` · `checkOutBeforeCheckIn`. Informational. |
| Timestamps | Returned in **UTC** (`Z`). Convert to local time for display. Same instant as what you sent. |

`GET /visits/stops/{stopId}/visit` on a stop never visited returns **200**:
`{ "visitId": null, "stopId": "…", "status": "pending", "checkIn": null, "checkOut": null, "updatedAt": "…" }`.
In the route pull, an unvisited stop has `"visit": null`.

## 9. Offline: `/push` changes

Keep the existing flow. Add these optional fields to the queued rows:

| Row | New fields |
|---|---|
| `checkIns[]` | `routeId`, `photoIds` |
| `checkOuts[]` | `checkInId`, `outcome`, `orders`, `noOrderReason`, `noOrderNote` (same meaning as §5) |

On reconnect, send in this order, as the app already does, waiting for each step:

```text
1. POST /visits/push   { checkIns: [ …all pending, oldest first ] }
2. POST /quotations    one per queued order, each with clientId + stopId
3. POST /visits/push   { checkOuts: [ …all pending, oldest first ] }
4. GET  /visits/routes/delta     → adopt stops[].visit
```

- **Buckets:** handle them as today. Delete `acceptedIds` locally, keep `rejectedIds` for retry, and drop `discardedIds`.
- **Leniency:** incomplete outcomes are *accepted* on `/push`, so don't rely on the server to catch them.
- **Partial failure:** if a stop's check-in isn't accepted in step 1, hold its check-out. The server tolerates either order, but holding keeps the visit clean.

## 10. Recommended client flow

```text
Open stop
  ├─ local state says "checked in"? → GET /stops/{id}/visit → adopt if different
  │
Tap CHECK IN
  ├─ generate checkInId, capture GPS + photos
  ├─ save locally (status checkedIn, unsynced)
  ├─ online?  POST /check-ins
  │     ├─ 200 → mark synced, store VisitDto
  │     ├─ 409 → adopt details (server visit), mark synced
  │     └─ network error → leave queued for /push
  └─ offline → queue for /push
  │
Take order(s)  → create quotation with clientId (+ stopId); queue if offline
  │
Tap CHECK OUT
  ├─ choose: [Check out with order]    → pick quotations taken at this stop (pre-select all)
  │          [Check out without order] → reason (cached list) + note if required
  ├─ validate locally (≥1 order / reason / note), same rules as §5
  ├─ save locally, then POST /check-outs (online) or queue for /push
  └─ 200 / 409 → adopt VisitDto
```

**Adopting server state:** after a successful sync, replace the stop's local state with the server's `visit`. Exception: a stop with **unsent local rows** keeps its local state until they are accepted.

## 11. Local database (Drift) changes

| Table | Add |
|---|---|
| check_outs | `checkInId TEXT`, `outcome TEXT` (`withOrder`/`withoutOrder`), `noOrderReason TEXT NULL`, `noOrderNote TEXT NULL` |
| check_out_orders (new) | `checkOutId`, `clientId`, `quotationServerId NULL`, `type` |
| check_ins | `photoIds TEXT` (JSON array), `routeId TEXT NULL` |
| quotations | `clientId TEXT UNIQUE`, `stopId TEXT NULL`, `serverId TEXT NULL` |
| no_order_reasons (new, cache) | `code PK`, `nameEn`, `nameKm`, `requiresNote`, `sort` |
| stops | `serverVisitJson TEXT NULL` (or columns) to hold the adopted `VisitDto` |

**Migration of existing rows:** queued check-outs without an outcome can be sent as they are. The server stores them as `unknown`.

## 12. Test checklist

- [ ] Online check-in → 200, stop shows checked in; repeat the same call → 200, no duplicate.
- [ ] Second phone checks in the same stop → 409 `AlreadyCheckedIn`; app adopts the server visit.
- [ ] Check-in with mock location → accepted, `flagged: true`.
- [ ] Check out without order with `other` and no note → blocked on the client (and 422 if sent).
- [ ] Check out with an order taken online → `linkStatus: linked`.
- [ ] Airplane mode: check-in → order → check-out; reconnect → push / quotations / push run in order; route delta shows the visit with the order `linked`.
- [ ] Order quotation sent after the check-out → `pending` then `linked` on the next pull.
- [ ] Reinstall the app → route pull restores today's check-ins and check-outs from `stops[].visit`.
- [ ] Revisit a completed stop → 409 `AlreadyCompleted` → offered an ad hoc visit.
- [ ] Reason list shows Khmer names and works offline.
- [ ] Create a quotation twice with the same `clientId` → second call 200 with the same quotation.

## 13. Known limits

- **Reason list:** the content and Khmer wording are provisional until sales ops confirms. There is no admin screen yet.
- **Sales orders:** `orders[].type = "salesOrder"` is accepted, but only quotations can be linked today.
- **Check-out location:** stored, not geofenced.
