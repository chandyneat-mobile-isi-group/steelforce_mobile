# Environments & release

Authoritative: `docs/skills/security.md` (release checklist),
`QA-engineering/` (device matrix, release checklist),
`docs/blueprint/migration-plan.md` §11 (branching). Release configuration is
**Type D** (`workflow.md` §2).

---

## 1. Environments

The app runs against at least **development**, **UAT/staging**, and
**production** backends.

- Environment values come from Envied config in `lib/core/config/`, generated
  from `.env*` files that are gitignored; `.env.example` is the committed
  template. iOS reads them through `ios/Flutter/Env.xcconfig`, generated by
  `tool/generate_ios_env.dart`.
- **Before changing anything here, find out how this repo selects an
  environment** (flavors, `--dart-define-from-file`, separate `.env` files) by
  reading `lib/core/config/`, `android/app/build.gradle*`, the Xcode schemes,
  and CI. Do not invent a mechanism. If none is documented, that is a finding
  to report.
- Every new config value is added to `.env.example` with a placeholder and a
  comment, in the same change. Never a real value.
- **No environment branching in feature code** (`if (isProd) …`). Read a
  config value; the environment decides it.
- Production values never appear in source, tests, fixtures, screenshots, or
  logs, and are never pointed at from a debug build.
- A debug-only shortcut must carry `// TODO(release-gate):` (`security.md` §5).

## 2. Versioning

- `pubspec.yaml` `version: MAJOR.MINOR.PATCH+BUILD`. The build number only ever
  increases; both stores reject reuse.
- Bump the version only when the user asks for a release change — never as a
  side effect of a feature.
- A schema change to the Drift database ships with its migration and a
  migration test in the same release (`architecture.md` §4). An installed app
  must upgrade from **every** version still in the field, not just the last one.

## 3. Release gate

Before calling anything release-ready, run `/release-check`. It must confirm,
with real results:

- `dart format --set-exit-if-changed .`, `flutter analyze`, and the full test
  suite pass.
- Release builds succeed for each shipped platform you can build here; say
  which you could not.
- No `TODO(release-gate)` remains reachable in a release build.
- Release builds use production config, obfuscation where the project enables
  it (`--obfuscate --split-debug-info`), and no debug logging of PII
  (`security.md` §3).
- Android and iOS permissions requested match what the features use: no
  leftover or widened permission in `AndroidManifest.xml` or `Info.plist`.
- Network config: no cleartext traffic, no `NSAllowsArbitraryLoads`.
- The `QA-engineering/` release checklist and device matrix are addressed.

## 4. Observability and rollback

- Crash and error reporting must be wired for release builds, with PII
  scrubbed. If the repo has none configured, report it as a release risk;
  do not add a vendor SDK without the user (`dependencies.md`).
- Keep the symbol files from `--split-debug-info` for every shipped build;
  without them, release stack traces cannot be read.
- **Mobile has no instant rollback** — a bad build stays on devices. Prefer
  server-side feature flags for risky behaviour, staged rollouts in Play
  Console and phased release in App Store Connect, and a `hotfix/*` branch
  from the release tag.

## 5. Never

- Run store upload, signing, or publishing commands. The user releases.
- Commit signing material, `key.properties`, or store credentials
  (`git-safety.md` §5).
